## Цел

Миграция от копие „bar-luna“ към бранд **Malts** с нова визия, нова база (нови таблици на същия сървър), промоции по период, подкатегории (≥3 нива), super admin контроли (маси, поръчки, повикване на сервитьор), локализация BG/EN/RO, зареждаща халба с бира; почистване на Luna/Bar референции. Архитектурата за **multi-brand** се проектира така, че да позволи следваща фаза без голямо пренаписване.

## Екип — консолидирани препоръки

- **UI/UX:** беж фон + черен текст за четимост; Moretti-червено за **primary CTA и акценти**, не за дълги параграфи; „Промотирано“ с отделен бадж + по възможност малък банер в карта; навигация при 3 нива — breadcrumb + ясна йерархия/accordion или двустепенни табове.
- **Skeptic:** multi-brand **не** да се гради пълноценно в v1, но схемата да позволява `brandId` или ясна граница за по-малко болка следваща фаза; централен админ като отделно приложение добавя експлоатационна тежест (N деплоя, N секрета).
- **Security:** super admin само със силна автентикация; feature flags и настройки с audit trail; публични API с rate limit; tenant/brand изолация на сървъра при обща платформа.
- **Performance:** индекси за `(productId, startAt, endAt)` при промоции; меню endpoint да връща дърво без N+1; при нужда кратък кеш на меню.

## Multi-brand: два подхода

**Зафиксирано (ADR):** [.knowledge-base/architectural-decisions/2026-04-08-multi-brand-platform-strategy.md](../architectural-decisions/2026-04-08-multi-brand-platform-strategy.md) — v1 с един бранд Malts + таблица `brands` и `brandId` в схемата; след v1 **по подразбиране** обща платформа със super-admin и строго сървърно `brandId` scoping; Approach A при ясни тригъри (изолация, договори, blast-radius).

По-долу е резюе за удобство; детайлите и последствията са в ADR.

### A) Отделен стек на бранд + централен „Администриране“ през API

**Плюсове:** изолация на данни и деплой; проблем в един обект не валди целия fleet; различни версии ако се наложи.  
**Минуси:** N инстанса, N бази или N схеми, N Pusher/Vercel проекти; централният панел трябва да поддържа много базови URL, ключове, контракти; оперативна тежест.

### B) Обща платформа (един Next.js + една БД с `brand_id`)

**Плюсове:** един деплой, един набор API, споделени подобрения; централният админ е „super-role + избор на бранд“ или отделен route group.  
**Минуси:** грешка/регресия може да засегне всички брандове; по-силна нужда от тестове, RLS или строги query филтри по `brand_id`.

**Пресечна точка на екипа за v1:** имплементирайте **Malls като единичен tenant**, но в схемата оставете **опционално поле `brandId`** (или таблица `brands` + FK) дори да има един ред — така преминаването към B по-късно е по-евтино от A, ако не изберете изрично A. Ако клиентът настоява за физическа сегрегация още от v2, миграцията от един към много deployment-и е по-ясна, ако домейнът и данните са вече абстрахирани по бранд в кода.

**Препоръка (вж. ADR):** по подразбиране **B** след v1; **A** при изрични тригъри в ADR.

### Фаза 4 — Меню и категории (клиент)

13. API меню: дърво от категории до 3+ нива + продукти с **effective price** (базова vs активна промо за `now`).
14. UX: breadcrumb / ясна навигация между нива; подобрена откриваемост при много категории (подреждане, секции, при нужда търсене в по-късен под-итерация).

### Фаза 5 — Админ панел

18. Super admin секция: **max tables**; **feature toggles** за поръчки и повикване на сервитьор; запис в audit log (препоръчително).

## Критерии за „готово“ (Definition of Done) за malls-v1

- Продукция/login на новата БД; без зависимости от старото име на база.
- Меню и админ работят с **3 нива** категории; промоции променят показваната цена в периода.
- BG/EN/RO без `de`; EUR+BGN коректно.
- Super admin може да зададе лимит маси и да спре/пусне поръчки и повикване на сервитьор; API отхвърля при изключено.
- Визия Malts + loader халба; домейн и копи съгласувани с Malts.
- Останалите open points по multi-brand са документирани в ADR, не блокират v1.
