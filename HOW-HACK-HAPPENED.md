# 🔍 Как е станал компромисът - Анализ

## 📋 Възможни сценарии за компромис

### Сценарий 1: Default Admin Credentials ⭐ **НАЙ-ВЕРОЯТНО (90%)**

**Как става:**
1. Атакуващият открива Next.js приложение на сървъра
2. Проверява за default credentials в документацията или seed файла
3. Намира `admin@lunabar.bg` / `admin123` в `prisma/seed.ts` или `USER_AUTH_SYSTEM.md`
4. Логва се успешно в администраторския панел
5. **НО:** Как качва XMRig от там?

**Възможни начини за качване на XMRig след login:**

#### Вариант А: Чрез SSH достъп
- Ако има SSH ключове или пароли в `.env` файла
- Ако има SSH достъп чрез друг начин
- След login в админ панела, може да има функционалност за изпълнение на команди (но не виждам такава в кода)

#### Вариант Б: Чрез уязвимост в upload endpoint-а
- Upload endpoint-ът валидира само image файлове
- НО: Ако имаше уязвимост преди (която е поправена), може да са качили shell script като image
- След това да са го изпълнили чрез някакъв начин

#### Вариант В: Чрез database injection
- Ако има SQL injection уязвимост (малко вероятно с Prisma)
- Може да са изпълнили команди чрез database functions

#### Вариант Г: Чрез други endpoints
- Може да има endpoint който изпълнява команди (не виждам такъв в кода)
- Може да има eval() или подобна функционалност (не виждам такава)

---

### Сценарий 2: SSH Compromise (25%)

**Как става:**
1. Слаба SSH парола или ключ
2. Brute force атака на SSH
3. Директен достъп до сървъра
4. Качва XMRig и настройва автоматично изпълнение

**Доказателства:**
- Провери `/var/log/auth.log` за failed SSH attempts
- Провери `last` и `lastlog` за подозрителни входове

---

### Сценарий 3: Уязвимост в зависимост (20%)

**Как става:**
1. Стара версия на Next.js или друга зависимост има уязвимост
2. Remote Code Execution (RCE) уязвимост
3. Атакуващият изпълнява команди директно
4. Качва XMRig

**Доказателства:**
- Провери `package.json` за стари версии
- Провери за известни уязвимости в използваните пакети

---

### Сценарий 4: Fallback Secret (60%)

**Как става:**
1. Атакуващият открива че `NEXTAUTH_SECRET` не е зададен
2. Използва известния fallback secret `dev-secret-change-in-production`
3. Генерира валиден JWT token за администратор
4. Логва се без да знае паролата
5. След това качва XMRig (същите въпроси като Сценарий 1)

---

## 🎯 Най-вероятният сценарий

**Комбинация от Сценарий 1 + Сценарий 2:**

1. Атакуващият използва default credentials (`admin@lunabar.bg` / `admin123`)
2. Логва се в администраторския панел
3. **НО:** Админ панелът няма директна функционалност за качване на произволни файлове или изпълнение на команди
4. **Следователно:** Най-вероятно е имало SSH достъп или уязвимост в зависимост
5. След login, атакуващият е използвал SSH или RCE за качване на XMRig

## 🔍 Как да проверим

### 1. Проверка на SSH логове
```bash
# Проверка за failed SSH attempts
grep "Failed password" /var/log/auth.log | tail -100

# Проверка за successful logins
grep "Accepted" /var/log/auth.log | tail -50

# Проверка на последните входове
last
lastlog
```

### 2. Проверка на application logs
```bash
# Проверка за login attempts
pm2 logs bar-luna --lines 1000 | grep -i "login\|auth\|failed"

# Проверка за подозрителни заявки
pm2 logs bar-luna --lines 1000 | grep -i "upload\|file\|exec"
```

### 3. Проверка на кога е създаден XMRig
```bash
# Проверка на file timestamps
ls -la /var/www/html/bar-luna/xmrig-6.24.0/
stat /var/www/html/bar-luna/xmrig-6.24.0/xmrig

# Проверка на кога е бил последно модифициран
find /var/www/html/bar-luna -name "*xmrig*" -exec ls -la {} \;
```

### 4. Проверка на cron jobs история
```bash
# Проверка на cron history (ако е наличен)
grep -r "xmrig\|miner" /var/log/cron* 2>/dev/null

# Проверка на systemd services
systemctl list-units --all --type=service | grep -i xmrig
```

## 🛡️ Защо админ панелът не може директно да качи XMRig

**Текущи ограничения:**
1. ✅ Upload endpoint валидира само image файлове (JPG, PNG, WebP)
2. ✅ Няма endpoint за изпълнение на команди
3. ✅ Няма eval() или подобна функционалност
4. ✅ Няма file system access освен за uploads директорията

**Следователно:**
- Ако компромисът е станал чрез админ панела, трябва да е имало:
  - Уязвимост в upload endpoint-а (която е поправена)
  - Или SSH достъп след login
  - Или уязвимост в зависимост

## 📊 Заключение

**Най-вероятно:**
1. Атакуващият е използвал default credentials за login
2. След това е използвал SSH достъп или уязвимост за качване на XMRig
3. Настроил е автоматично изпълнение чрез cron job или systemd service

**Препоръки:**
- Изпълни cleanup скриптовете
- Смени всички пароли и секрети
- Укрепете SSH достъпа
- Провери логовете за точна причина
- Мониторирай за подозрителни активности
